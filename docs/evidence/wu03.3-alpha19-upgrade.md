# WU3.3 — alpha19 dependency upgrade probe

## Trigger and hypothesis

WU3.2 pinned `androidx.compose.remote` at `1.0.0-alpha18` and found that the alpha18 API-6 direct-paint control (`RemoteComposeWriter(600, 600, "Clock", 6, 0, platform)` + `drawCircle(150, 150, 150)`) painted only a clipped black arc across the top 11 control-local rows, with no visible circle body, while the legacy four-argument `paint-probe` stayed fully blank. This was evidence that the writer/header/API-level path discriminates behavior, but was explicitly **not a GO**.

Google's Maven metadata confirms `androidx.compose.remote:remote-core` published `1.0.0-alpha19` on 2026-09-09 (before this diagnostic sequence began). Its public changelog lists:

- "Fixed density behavior scaling for `RemoteDp` values — resolves scaling issues across remote-compose modifiers, arrangements, and shapes."
- "Fix horizontal alignment for autosized and centered/right-aligned complex text."

A density/scaling bug is a plausible explanation for a circle that paints only its top edge instead of its full body, so this work unit tests whether the alpha19 bump changes either diagnostic fixture's rendering, without yet doing the deeper four-arg-vs-six-arg header/serialization comparison WU3.2 recommended.

**This is a diagnostic dependency-version probe only.** It does not modify WU2's canonical creator, contract, or `scheduled-match.rc` fixture.

## Hypothesis and decision table

| Pixel_9 post-attach outcome under alpha19 | Decision | WU3.3 result |
| --- | --- | --- |
| Both fixtures render fully (navy/yellow background+circle for the probe; full 300px circle for the control) | Alpha19 fixes the blank/clipped render; re-run WU3 gate under alpha19. | Not observed. |
| API-6 control renders more/less of the circle than WU3.2, or the legacy probe changes at all | Alpha19 partially affects the renderer; quantify the delta and keep investigating. | Not observed. |
| Both fixtures produce byte-for-byte identical app-content crops to WU3.2's alpha18 results | Alpha19's density/text fixes do not touch this failure mode; continue with the four-arg-vs-six-arg header/serialization comparison WU3.2 recommended. | **Observed.** |
| Installation, resume, or hash assertion fails, or alpha19 is a breaking dependency bump | Diagnose packaging/compatibility before making a visual claim. | Not observed — alpha19 compiled, built, and ran without any code changes. |

**Verdict: NO-GO / no change.** Upgrading to alpha19 is a drop-in dependency bump (no source changes required) but produces **pixel-identical** app-content output to WU3.2's alpha18 run for both fixtures: same 878-pixel difference, same bounding box `(94, 0, 206, 11)`, same channel deltas. The density-scaling and text-alignment fixes shipped in alpha19 do **not** affect this failure mode. The root cause remains in the writer/header/API-level path (four-arg vs. six-arg `RemoteComposeWriter`) or another public runtime requirement, as WU3.2 concluded — it is not fixed by this dependency version.

## Device evidence

### Methodology correction: device selection

The environment's already-running `emulator-5554` instance turned out to be `Pixel_10_Pro` / API 36 (Android 16), not `Pixel_9` / API 35 used by every prior work unit. Using it would have confounded an alpha19-vs-alpha18 comparison with a device/OS-version change. That emulator was killed and the `Pixel_9` AVD was booted fresh, coming up as `emulator-5556`. Its identity was confirmed to exactly match WU3.2's `Pixel_9` fingerprint (`google/sdk_gphone64_arm64/emu64a:15/AE3A.240806.043/12960925:userdebug/dev-keys`); see `wu03.3/device-identity.txt`. All device evidence below uses `emulator-5556` (Pixel_9/API 35), keeping the device variable controlled.

### Screenshot and pixel result

Both screenshots are 1080×2424. Analysis uses the identical crop/methodology as WU3.2: app-content crop `(x=0..1079, y=289..2375)`, excluding status/activity chrome and the gesture/navigation area — 2,253,960 pixels.

- **Legacy paint probe (alpha19):** 45 crop colors; dominant background `#f1f0f7` is 2,233,440 pixels (99.0896%); exact expected navy `#002b5c` and yellow `#ffff00` counts are both zero. Identical distribution to WU3.2's alpha18 run.
- **API-6 control (alpha19):** 97 crop colors, same dominant background. It differs from the legacy crop at **878 pixels** (0.038954%), bounding box `x=94..205`, control-local `y=0..10` — **identical count and bounding box to WU3.2's alpha18 result.** 768 changed pixels are exact black, same as WU3.2.
- No changed pixels occur below control-local row 10 under alpha19 either. The circle body remains absent.
- Full-file screenshot SHA-256 hashes differ from WU3.2's (`wu03.3/screenshot-sha256.txt`) because of non-deterministic chrome outside the crop (e.g. the status-bar clock), not because of any app-content difference — the crop-level pixel comparison above is the controlled comparison and shows no change.

Raw screenshots, zoomed top-edge crops, SHA-256 receipts, and the reproducible Pillow criterion/difference calculation are in `wu03.3/`; see `pixel-analysis.txt` and `screenshot-sha256.txt`.

### Process-scoped logcat

Each cold launch clears logcat, obtains that app process PID, then captures `adb logcat --pid <pid> -d -v threadtime`. The required pattern search for `RemoteComposePlayer`, `Error loading document`, `Error setting document`, `Unsupported document`, and `exception` returned no matches for either launch under alpha19 (`wu03.3/*-logcat-audit.txt`), matching WU3.2.

The legacy probe raw log still contains the same four `System.err: error unknown Paint Type 14` warnings under alpha19. The API-6 control raw log still does not. This confirms the warning is unrelated to the alpha18→alpha19 bump.

## Conclusion

Upgrading to `1.0.0-alpha19` is safe (no source changes, all existing tests pass) but does **not** change the blank/clipped-render outcome at all — the app-content pixel comparison to WU3.2 is exact. The alpha19 density-scaling and text-alignment fixes are not the relevant code path for this failure. **Recommendation: keep the dependency at alpha19 going forward (it's a strict, harmless upgrade with real fixes for other paths) but do not treat this as resolving the blank-render investigation.** The next diagnostic step remains WU3.2's original recommendation: compare the four-argument vs. six-argument `RemoteComposeWriter` serialization/header path directly (byte-level document inspection), since that is the only path shown to date to change the outcome.
