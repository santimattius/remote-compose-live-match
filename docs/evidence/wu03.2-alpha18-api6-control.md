# WU3.2 — alpha18 API-6 direct-paint control

## Provenance and fixture contract

The control is pinned to AndroidX alpha18 release snapshot
[`0f510de14252cfbba4cf679e0f847d84f7821531`](https://android.googlesource.com/platform/frameworks/support/+/0f510de14252cfbba4cf679e0f847d84f7821531), source:

`compose/remote/integration-tests/player-view-demos/src/main/java/androidx/compose/remote/integration/view/demos/examples/old/BasicProceduralDemos.java`

Its `simple1()` sequence is reproduced exactly apart from the required JVM platform substitution:

```java
new RemoteComposeWriter(600, 600, "Clock", 6, 0, platform);
rcDoc.drawCircle(150, 150, 150);
return rcDoc;
```

`JvmRcPlatformServices()` is the sole platform substitution. The control adds no color, root, layout, or other operation. It deliberately selects the alpha18 six-argument writer/API-6 path, unlike the retained legacy four-argument paint probe. The alpha18 sources distinguish those constructors: four arguments create a default `RemoteComposeBuffer` and call `header(...)`; six arguments create `RemoteComposeBuffer(apiLevel)`, call `setVersion(apiLevel, profiles, ...)`, then `addHeader(...)`.

The source snapshot's `DocPlayerActivity` path creates `RemoteComposePlayer`, calls `player.setDocument(bytes)`, then adds the player to the host. This work unit keeps the existing app adapter and compares both fixtures through the same debug activity post-attach route.

## Hypothesis and decision table

**Hypothesis:** if the alpha18 API-6 document paints where the legacy four-argument probe does not, the serialized writer/header/API-level path is the discriminating variable. This fixture test does not establish visual success.

| Pixel_9 post-attach outcome | Decision | WU3.2 result |
| --- | --- | --- |
| API-6 control visible; legacy probe blank | Investigate the legacy writer/header path. | **Observed, but partial:** the control renders only a black top arc; the legacy probe is blank. |
| Both controls blank | Continue investigating player/document compatibility or required public runtime conditions. | Not observed. |
| Both controls visible | Reassess the prior blank-render environment and evidence conditions. | Not observed. |
| Installation, resume, or hash assertion fails | Diagnose packaging or lifecycle before making a visual claim. | Not observed. |

**Verdict:** the API-6 control provides a real but clipped document-paint signal, while the legacy probe remains blank. This is evidence that the writer/header/API-level path discriminates behavior. It is **not a GO for complete document rendering**: the expected 300 px circle body is absent below the top 11 control-local rows. The next investigation should compare the legacy four-argument serialization/header path with the six-argument API-6 path; it must not claim a fully rendered document.

### Screenshot and pixel result

Both screenshots are 1080×2424. Analysis excludes status/activity chrome (`y=0..288`) and gesture/navigation area (`y=2376..2423`), using the shared app-content crop `(x=0..1079, y=289..2375)`: 2,253,960 pixels.

- **Legacy paint probe:** 45 crop colors; dominant background `#f1f0f7` is 2,233,440 pixels (99.0896%); exact expected navy `#002b5c` and yellow `#ffff00` counts are both zero. The screenshot is blank in the app content area.
- **API-6 control:** 97 crop colors with the same dominant background. It differs from the legacy crop at 878 pixels (0.038954%), bounding box `x=94..205`, control-local `y=0..10` (screen `y=289..299`). 768 changed pixels are exact black. The paired top-edge crops show a black circular cap immediately below the app chrome, geometrically consistent with the top of `drawCircle(150, 150, 150)`.
- No changed pixels occur below control-local row 10, so the expected 300 px circle body is not visible. This is why the partial cap is evidence of the API-6 path rather than a complete render verdict.

Raw screenshots, zoomed top-edge crops, SHA-256 receipts, and the reproducible Pillow criterion/difference calculation are in `wu03.2/`; see `pixel-analysis.txt` and `screenshot-sha256.txt`.

### Process-scoped logcat

Each cold launch clears logcat, obtains that app process PID, then captures `adb logcat --pid <pid> -d -v threadtime`. The required pattern search for `RemoteComposePlayer`, `Error loading document`, `Error setting document`, `Unsupported document`, and `exception` returned no matches for either launch (`wu03.2/*-logcat-audit.txt`).

The legacy probe raw log does contain four `System.err: error unknown Paint Type 14` warnings. The API-6 control raw log does not. These warnings do not match the required search strings, but they reinforce that the legacy path remains distinct; they do not establish a root cause.
