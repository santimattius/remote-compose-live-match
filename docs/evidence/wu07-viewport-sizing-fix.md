# WU7 — viewport sizing fix (small-card finding)

## Finding

The user flagged (via screenshot, mid-WU6) that the rendered Scheduled card looked "very small": a
navy box confined to roughly the top-left 30%-width/7%-height of a 1080x2424 Pixel_9 screen, with
the rest of the screen left blank. All three canonical documents (`scheduled-match.rc`,
`live-match.rc`, `finished-match.rc`) declared a fixed `Viewport(320, 180)`.

## Investigation: does `RemoteComposePlayer` support scale-to-fit?

Decompiled the alpha19 `remote-player-view` runtime jar (no sources jar available, same approach
as WU6's `DrawTextAnchored` investigation):

- `RemoteComposePlayer`'s full public method surface (`javap -p`) has **no** scale/fit/content-scale
  API. Its only sizing-adjacent private method, `applyContentBehavior(int)`, wraps the inner view in
  a `HorizontalScrollView`/`ScrollView` for scroll behavior — unrelated to scaling.
- `RemoteComposeView.onMeasure(int, int)`: `measureDimension(spec, documentSize)` returns the exact
  parent-given size when the `MeasureSpec` mode is `EXACTLY` (ignoring the document's own declared
  width/height entirely), `min(specSize, documentSize)` for `AT_MOST`, and `documentSize` for
  `UNSPECIFIED`. Since both `MainActivity` and `DiagnosticPlaybackActivity` host the player via
  `AndroidView(modifier = Modifier.fillMaxSize()...)`, Compose gives it `EXACTLY` constraints
  matching the full available content area — so the **view** always measures full-screen already
  (this matches WU3.4/3.5's earlier finding that the player itself was never the size problem).
- `RemoteComposeView.onDraw(Canvas)`: sets `AndroidRemoteContext.mWidth/mHeight` to the view's
  actual `getWidth()/getHeight()` (the full-screen pixel size), then calls
  `RemoteDocument.paint(mARContext, theme)` directly. **No `canvas.scale(...)` call exists anywhere
  in this path.**
- Conclusion: our creator draws with absolute pixel coordinates (`drawRect(0,0,320,180)`,
  `drawTextAnchored(text, 16f, 32f, ...)`) baked into the document at creation time. There is no
  public API — on the player or in this drawing style — that scales those baked absolute
  coordinates to the actual (larger) view size. The "small card" was not a rendering bug; it was a
  document authored at literal small pixel dimensions being drawn 1:1 into a much bigger canvas.
  (A different authoring style — the library's relative/fill-based layout-component DSL, which this
  project's raw procedural `drawRect`/`drawTextAnchored` calls do not use — could pick up the
  context's width/height and adapt; that's out of scope for this WU.)

**Fix applied (fallback path, since no scale-to-fit API exists):** author the documents at pixel
dimensions that actually correspond to the real device — `Viewport(1080, 480)` (1080 matches the
Pixel_9's physical width; 480 gives a full-width banner card, roughly 20% of screen height, with
room for up to four text lines) — instead of the arbitrary `Viewport(320, 180)`. Text size was also
made explicit (`RcPaint.setTextSize(48f)`, previously relying on the library default, which was
comparatively tiny against the enlarged canvas) and text positions were rescaled to fill the new
canvas with sensible spacing.

## Changes

- `ScheduledFixtureGenerator.kt`, `LiveFixtureGenerator.kt`, `FinishedFixtureGenerator.kt`:
  `Viewport(320, 180)` → `Viewport(1080, 480)`.
- `ProceduralJvmMatchDocumentCreator.kt`, `ProceduralJvmLiveMatchDocumentCreator.kt`,
  `ProceduralJvmFinishedMatchDocumentCreator.kt`: added `setTextSize(TEXT_SIZE)` (48f) to the text
  paint, widened left padding to `PADDING_X` (48f), and respaced line `y` positions for the taller
  canvas (Scheduled/Finished: 100/210/320; Live: 90/190/290/390).
