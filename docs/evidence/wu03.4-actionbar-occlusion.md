# WU3.4 — root cause: default ActionBar occludes document content

## Hypothesis and decision table

Two hypotheses were tested in order, cheapest first.

| Step | Hypothesis | Test | Result |
| --- | --- | --- | --- |
| 0 | `RemoteComposePlayer` view is laid out with a collapsed/small height (view-sizing bug), independent of document encoding. | Dump the live view hierarchy for `DiagnosticPlaybackActivity` in `post_attach` mode via `adb shell uiautomator dump`. | **Falsified.** The player `FrameLayout` bounds are `[0,0][1080,2424]` — full screen. |
| 1 | The four-arg vs six-arg `RemoteComposeWriter` header/serialization path is the discriminating variable (WU3.2's original recommendation). | N/A — superseded before being tested, see below. | **Not reached / moot.** |
| 1b (actual) | The plain `Activity`'s default `ActionBar` (opaque, `[0,0][1080,289]`) is compositely drawn on top of the full-screen player view, and every diagnostic document to date happens to paint its content entirely or mostly inside that occluded band. | Call `actionBar?.hide()` before `setContentView`, rebuild, re-run both existing fixtures unchanged, screenshot. | **Confirmed.** |

The view hierarchy dump (Step 0) already contained the answer that reframed the whole WU3–WU3.3 investigation: `android:id/action_bar_container`, bounds `[0,0][1080,289]`, is a **sibling** of `android:id/content` under `decor_content_parent` — i.e. an overlay compositing on top of the player, not a sibling inside a shared layout that would push the player down. The player itself was never resized or clipped; its content was drawn correctly underneath opaque chrome.

## Why every prior diagnostic looked like a document/player bug

- `paint-probe.rc` (legacy 4-arg path): document viewport is `320x180` (`DiagnosticFixtureGenerator.WIDTH/HEIGHT`). Rendered at 1:1 device pixels anchored at the player's origin `(0,0)`, its entire `0..180`px height sits inside the ActionBar's `0..289`px occlusion band. **100% of the content was always hidden.** This is also true of `MainActivity`'s real fixture, `scheduled-match.rc` (`fixtures/scheduled-match.manifest`: `viewport=320x180`, same creator pattern in `ProceduralJvmMatchDocumentCreator`) — see confirmation below.
- `alpha18-api6-control.rc` (6-arg API-6 control): `drawCircle(150,150,150)` in a `600x600` document, so the circle spans document/device y=`0..300`. Only the sliver from y=`289..300` (11px) falls below the occlusion band — exactly the 878px arc WU3.2/WU3.3 measured at bounding box `x=94..205, y=0..10` (crop-local, i.e. absolute `y=289..299`).

No document/protocol/player compatibility difference was ever needed to explain any prior result. WU3.2's four-arg vs six-arg comparison is superseded: both writer paths produce fully correct, fully visible output once the occlusion is removed (see below), so **Step 1's original plan (byte-level header comparison) is no longer needed** — there was nothing wrong with either serialization path.

No fixture, creator, contract, or adapter code changed. `checkDiagnosticFixture` still passes (fixture bytes identical to WU3.2/WU3.3).

## Confirmation on the real fixture (`MainActivity` / `scheduled-match.rc`)

To confirm this is the actual WU3 gate's root cause and not just a diagnostic-activity artifact, `MainActivity.kt` was **temporarily** given the same one-line `actionBar?.hide()`, rebuilt, and launched with the real `scheduled-match.rc` fixture (`viewport=320x180`, from `fixtures/scheduled-match.manifest`). Result: the navy-filled `320x180` rectangle became visible in the top-left corner (previously 100% hidden, matching every WU3–WU3.3 "blank screenshot" result). `MainActivity.kt` was reverted immediately after this confirmation — **no production fix is included in this diagnostic work unit**; that edit was not committed to any file and is not part of this WU's diff.

A secondary, independent defect was exposed once occlusion was removed: `ProceduralJvmMatchDocumentCreator.create()` calls `drawTextAnchored(...)` for the two team names and kickoff time without ever calling `getRcPaint().setColor(...)` first, unlike `DiagnosticFixtureGenerator`'s paint probe. The team-name/time text is therefore drawn in whatever the default/unset paint color is, indistinguishable against the navy background in this manual check. This is a separate, easily fixable follow-up (explicit text paint color), out of scope for this diagnostic WU, and is logged in `docs/alpha-learnings.md` for whoever picks up the real production fix.

## Verdict

**Root cause found and confirmed, not a document/player/protocol compatibility issue.** The entire WU3 → WU3.3 "blank/clipped render" investigation was chasing a false lead: the default `Activity` `ActionBar` was compositing opaquely over the full-screen `RemoteComposePlayer`, and every tested document (real and diagnostic) happened to paint content sized/positioned such that it fell entirely or mostly within the occluded band. Removing the ActionBar (or, for a production fix, using a no-action-bar theme, or explicitly measuring/positioning the player below the chrome instead of relying on `setContentView` default full-bleed placement) makes both diagnostic fixtures render pixel-correct, and makes the real `scheduled-match.rc` document's background rectangle visible for the first time in this project's history.

**This is a GO signal that AndroidX Remote Compose alpha18/alpha19 rendering itself works correctly** for the tested constructs (rects, circles, the 4-arg and 6-arg writer paths). It is **not yet a GO for the full WU3 visual gate**: that requires a real production fix (not a temporary diagnostic-only edit) plus re-running WU3's original gate criteria, and separately fixing the newly-exposed missing-text-color defect so the real document's text is visible too.
