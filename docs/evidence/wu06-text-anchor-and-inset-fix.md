# WU6 — flush-left text anchoring and system-bar inset fix

Fixes both findings logged in `docs/alpha-learnings.md` from WU4/WU5 (2026-09-19): `drawTextAnchored` center-anchor text clipping, and the system status bar overlapping document content. Kept as a single work unit — both fixes are small, and re-verification exercises all three existing fixtures together.

## Finding 1: `drawTextAnchored` anchor mode

**Investigation.** No sources jar is resolvable for `androidx.compose.remote:remote-core`/`remote-creation-core` alpha19, so the compiled classes were decompiled with `javap -c -p` directly (`androidx/compose/remote/core/operations/DrawTextAnchored.class`). The `paint(PaintContext)` method computes the actual draw position as `mOutX + getHorizontalOffset()` / `mOutY + getVerticalOffset(baseline)`. Reconstructing `getHorizontalOffset()`'s bytecode arithmetic:

```
w = mBounds[2] - mBounds[0]                     // measured text width
offset = -(w * (1 + panX)) / 2 - mBounds[0]
```

With `panX = 0` (previously used everywhere): `offset = -w/2 - mBounds[0]` — centers the text on `(x, y)`, confirming the WU4/WU5 finding. With `panX = -1`: `offset = -mBounds[0]` — draws the text so its own left bound sits at `x`, i.e. flush-left. With `panX = +1`: `offset = -w - mBounds[0]` — flush-right. This is a real, symmetric anchor parameter (`-1`/`0`/`+1` = left/center/right), not a workaround — it's the general, correct fix, applied consistently rather than reformatting individual strings.

**Fix applied**: changed every `drawTextAnchored(text, x, y, panX, panY, flags)` call's `panX` from `0f` to `-1f` in `ProceduralJvmMatchDocumentCreator` (Scheduled), `ProceduralJvmLiveMatchDocumentCreator`, and `ProceduralJvmFinishedMatchDocumentCreator`. `panY` (vertical anchor, still `0f`/centered) was left unchanged — no vertical-clipping symptom was reported, and vertical centering on each line's fixed `y` was already visually verified as correct in WU3.5/WU4/WU5.

**Strict TDD.** Added `textIsAnchoredFlushLeftNotCentered()` to all three creator test files, asserting the encoded document bytes contain the IEEE-754 bit pattern for `-1.0f` (`0xBF800000`, either endianness), mirroring the existing `containsColorLiteral` byte-pattern-search style already used in this suite (`explicitBackgroundAndTextColorsAreEncodedInTheDocument`). RED confirmed for the right reason (`AssertionError`, pattern absent) against the unmodified `panX = 0f` code; GREEN after the three-line change.

## Finding 2: system status bar overlapping document content

**Fix applied**: added `.windowInsetsPadding(WindowInsets.systemBars)` to the `AndroidView`'s `Modifier` (in addition to the existing `Modifier.fillMaxSize()`) in both `MainActivity` and `DiagnosticPlaybackActivity`. The outer `Surface` keeps `Modifier.fillMaxSize()` alone, so the screen background remains edge-to-edge; only the `RemoteComposePlayer`'s content area is inset away from the system status/navigation bars. This does not reintroduce WU3.4's `ActionBar` occlusion (the `NoActionBar` theme is untouched) — it addresses a different mechanism (system-bar foreground glyphs overlapping content drawn at the view's origin, not an opaque app-level chrome container).
