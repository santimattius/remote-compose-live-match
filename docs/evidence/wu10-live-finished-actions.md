# WU10 — wire `open_match`/`open_highlight`/`open_summary` into Live and Finished

## Summary

Extends WU9's proven action-dispatch pattern (real `RemoteComposeWriter.addClickArea` button +
`RemoteComposePlayer.addIdActionListener` registered **after** `setDocument`, validated against
`ActionAllowlist`) to the remaining three catalog actions: `open_match` and `open_highlight` in
the Live document, and `open_summary` in the Finished document. All three now have a real,
device-confirmed end-to-end tap path, matching the bar WU9 set (a genuine `adb shell input tap`,
not just `View.performClick()`).

Kept as a single cohesive WU10 slice (not split into WU10/WU11): the creator changes for both
documents are small and mechanically identical to WU9's pattern, and splitting them would have
meant re-deriving the same host-wiring investigation twice for no benefit.

## Investigation: why the first device run showed zero `ClickAreaView`s

The very first host-wiring attempt used `DiagnosticPlaybackActivity`'s existing
`MODE_POST_ATTACH` path (`player.post { load(player, fixture) }`), matching how WU4–WU7's
screenshot evidence was captured. Both new instrumentation tests failed with zero click areas
found in the live view tree.

To isolate document-encoding bugs from view-materialization bugs, added a temporary reflection
probe (not part of the final diff) that read `RemoteComposeView.mInner.mDocument.getDocument()
.getClickAreas()` directly:

- **Live**: `getClickAreas()` returned a list of size `2` — the click-area operations *were*
  correctly parsed into the document model, with the exact authored bounds and wire-value text
  visible in the document's own `toString()` dump (`CLICK_AREA <49 <50> <51>+48.0 450.0 528.0
  530.0+`, `CLICK_AREA <52 <53> <54>+552.0 450.0 1032.0 530.0+`).
- **Finished**: `getClickAreas()` returned size `1`, same pattern.
- In both cases, the live `RemoteComposeView`'s **child count was `0`** — no `ClickAreaView` had
  been added to the view hierarchy, despite the document model having the areas.

Switching the same probe to `MODE_PRE_ATTACH` (load synchronously in the `AndroidView` factory,
before the view is returned/attached — the same timing `MainActivity` already uses in
production) changed the child count to `2` (Live) and `1` (Finished), matching the document
model. This isolates the defect to `updateClickAreas()`'s child-view creation running only
during the initial attach/layout pass, not being re-triggered by a later `setDocument()` call
that swaps in a document with click areas.

This is now `docs/alpha-learnings.md`'s dated entry; `MODE_PRE_ATTACH` was used for all further
device evidence in this WU. `MainActivity` is unaffected (it already always loads before attach).
